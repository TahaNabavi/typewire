# v0.1.0 — GraphQL, without a second client

`@tahanabavi/typefetch-graphql` makes a GraphQL endpoint an ordinary route in a
typefetch contract. Not a GraphQL client living beside your HTTP one, with its
own cache, its own auth setup and its own error shape — the *same* client, the
same middleware chain, the same `onError`, the same retry policy, the same mock
mode and the same devtools timeline.

The reason this is worth a package rather than a fork: GraphQL-over-HTTP is a
POST with a body. Only four things vary per wire, and they are the entire
adapter interface — build the request, decode a 2xx, normalize a failure,
describe yourself to tooling.

---

## 1. The selection set is generated from your Zod schema

This is the thing no other GraphQL client can do, and the reason to pick this
one.

```ts
profile: {
  transport: "graphql",
  operation: "query",
  root: "user",
  request: z.object({ id: z.string() }),
  response: z.object({ id: z.string(), name: z.string(), email: z.string() }),
}
```

sends:

```graphql
query UserProfile($id: String!) { user(id: $id) { id name email } }
```

No document is written, and none is kept in sync. Add `email` to the response
schema and the query asks for it; remove it and the query stops. With a
hand-written document the query and the type that validates its result are two
files that agree only until someone edits one of them — and the failure mode is
a `null` reaching a component three screens from its cause.

It is built on `z.toJSONSchema()` (zod v4), so there is no schema walker to rot.

**Variables become the root field's arguments** — `user(id: $id)` — which is the
convention that makes the common case need no configuration at all. Types are
inferred from the request schema and overridable per variable:

```ts
variableTypes: { id: "ID!" }
```

### When generation is refused

Deliberately, and with the schema path in the message:

| Schema | Why |
| --- | --- |
| a union or `z.record()` in the response | there is no single unambiguous selection set |
| a cyclic schema | the selection would not terminate |
| variables with no `root` | no field to attach the arguments to |
| a scalar response with no `root` | nothing to select |

Each of these is a case where a *guess* would produce a query that runs and
returns the wrong thing. Write `document` explicitly instead — which is also
what fragments, aliases and unions want.

## 2. Both response shapes

GraphQL-over-HTTP has two, and they disagree about what a failure looks like:

| Media type | Failure |
| --- | --- |
| `application/json` (legacy) | HTTP **200**, with `errors` inside the envelope |
| `application/graphql-response+json` | a real 4xx/5xx |

Both are handled. The legacy one is the interesting case: a 200 that is actually
an error can only be detected while decoding, so `decode` throws a `RichError` —
putting it on the client's normal failure path, so `onError`, retries and
instrumentation behave exactly as they do for any other transport.

## 3. Errors normalize

`extensions.code` is a convention rather than a spec, so this maps the codes the
ecosystem actually emits — Apollo Server's set, which everything else copied —
onto typefetch's shared `ErrorKind`:

| `extensions.code` | `ErrorKind` |
| --- | --- |
| `UNAUTHENTICATED` | `unauthenticated` |
| `FORBIDDEN` | `permission_denied` |
| `BAD_USER_INPUT` · `BAD_REQUEST` | `invalid_argument` |
| `NOT_FOUND` | `not_found` |
| `CONFLICT` | `already_exists` |
| `TOO_MANY_REQUESTS` | `resource_exhausted` |
| `INTERNAL_SERVER_ERROR` | `internal` |
| `SERVICE_UNAVAILABLE` | `unavailable` |
| `TIMEOUT` | `deadline_exceeded` |

That mapping is the whole point of the transport being part of typefetch: an
app's "redirect on `unauthenticated`" handler fires for a GraphQL
`UNAUTHENTICATED` exactly as it does for an HTTP 401.

A server that sends no code but a real status still gets a useful
classification. The legacy 200-with-errors case with no code falls through to
`unknown`, which is honest — nothing in the response says what went wrong.

## 4. Partial data

```ts
errorPolicy: "none" | "all"   // default: "none"
```

`"none"` rejects when `errors` is non-empty. `"all"` resolves with `data` when
there is some — and calls `onPartialErrors` with what was dropped, because
resolving half a result while silently discarding the reason for the other half
is how a `null` reaches a UI far from its cause.

## 5. API

| Export | Purpose |
| --- | --- |
| `graphqlTransport(config?)` | The adapter. Pass to `transports` at the setup site. |
| `generateDocument(input)` | The selection-set generator, standalone |
| `operationNameFrom(endpointId)` | `user.profile` → `UserProfile` |
| `kindFromGraphqlCode(code, status)` | The error mapping, standalone |
| `DocumentGenerationError` | Thrown with the offending schema path |

```ts
graphqlTransport({
  url,                 // default: `${baseUrl}/graphql`
  method,              // "GET" for queries — mutations always POST
  headers,
  errorPolicy,
  onPartialErrors,
})
```

`method: "GET"` applies to queries only. A mutation over GET is cacheable by
anything between the client and the server, which is a way to lose a write.

## 6. Contract fields

| Field | Meaning |
| --- | --- |
| `transport: "graphql"` | selects this adapter |
| `operation` | `"query"` \| `"mutation"` |
| `root` | the field variables attach to, and the selection root |
| `document` | an explicit document — skips generation entirely |
| `operationName` | defaults to the endpoint id, PascalCased |
| `variableTypes` | override an inferred GraphQL type per variable |
| `errorPolicy` | per-route override of the client default |

These exist on the endpoint type **only when this package is a dependency** —
they are merged into typefetch's open `TransportRegistry` by declaration
merging. A contract that names `transport: "graphql"` without the package
installed does not typecheck, which is the correct answer.

## 7. Backward compatibility

Nothing to break — this is the first release. Notably it required **zero changes
to `@tahanabavi/typefetch`**: it was built entirely outside the core as the
first test of whether the transport seam was real. If it had needed even one
core change, the seam was wrong, and that was the cheapest possible moment to
find out.

Zero runtime dependencies, asserted in CI.

## 8. Deliberately out of scope

- **Subscriptions.** They are a different transport (WS/SSE), not a different
  document — `@tahanabavi/typesocket` is the right home.
- **A normalized cache.** `typefetch-query-core` caches by `endpointId` + input,
  the same as every other transport. Entity-level normalization is a distinct
  design with distinct trade-offs.
- **Fragment composition helpers.** `document` accepts anything; a fragment
  registry is a codegen concern.
