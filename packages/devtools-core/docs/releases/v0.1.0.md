# v0.1.0 — one timeline, once there was more than one wire

`@tahanabavi/type-devtools-core` is the headless store an inspector is built on:
a ring buffer of events, an override registry, a latest-only progress channel,
and a live mirror of a query cache. It imports nothing — not typefetch, not
typesocket, not the query engine — because every client it reads is typed
structurally.

That design was already right. What this release fixes is that the bridge was
built when "which transport" and "which client" were the same question, and
typefetch's transport registry made them different ones.

---

## 1. `source` is the client; `transport` is the wire

One typefetch client now speaks REST, GraphQL and gRPC. Every one of those calls
arrives at the bridge through `connectTypeFetch`, so every one of them is
`source: "http"` — and before this release, that was the only thing an entry
recorded. A GraphQL query and a REST GET were indistinguishable on the timeline.

`InspectorEvent` and `InspectorEntry` now carry both:

|             | means                                                                                          | present                     |
| ----------- | ---------------------------------------------------------------------------------------------- | --------------------------- |
| `source`    | which **client** produced it — `"http"` (typefetch), `"ws"` (typesocket)                       | always                      |
| `transport` | which **wire** carried it — `"http"`, `"graphql"`, `"grpc"`, or a third-party adapter's `kind` | when the client reports one |

The obvious alternative — widening `source` to `"graphql"` and `"grpc"` — is
wrong, and quietly so. `source` is the key space for two things:

```ts
bridge.setOverride('http', 'user.profile', { mock }) // keyed (source, label)
;`${source}:${id}` // the correlation key
```

The connector that resolves an override for a GraphQL endpoint is
`connectTypeFetch`, which asks for `getOverride("http", …)`. An override
registered under `"graphql"` would be accepted, listed in the panel, and never
match anything — the worst possible failure for a debugging tool. So `source`
stays per-client and stable; `transport` is the new axis.

**Show `transport` in a UI. Key on `source`.**

### The default is not a guess

A typefetch older than the transport registry emits no `transport` at all. The
connector fills in `"http"` rather than leaving it blank, because every call
that client could possibly make was HTTP — a blank would render as "unknown
wire" for a client that only ever had one. typesocket reports none either, and
needs none: it has exactly one wire and says so through `source`.

`selectEntries` hoists the wire from the event that **opened** the call. The
concluding event names none, so first-seen wins for the row rather than last.

## 2. `errorKind` — the failure, named the same way on every wire

typefetch classifies every failure into a normalized `ErrorKind` (the gRPC
status set, plus `network` and `validation`). The bridge was dropping it, and
recording `status` instead — a field that is meaningful on exactly one of the
three wires typefetch now speaks.

```ts
entry.errorKind // "not_found", from HTTP 404, gRPC code 5,
// or GraphQL extensions.code: "NOT_FOUND"
```

It is lifted onto the entry rather than left inside the error, so a panel never
walks a transport-specific body to find out what went wrong. Without it, a
failed gRPC row could only say `error`: true, and useless.

The hoist reads `event.meta.kind` rather than digging into `payload`, so each
connector decides what counts as the normalized kind for its transport and
`selectEntries` stays transport-agnostic. A connector that classifies nothing
leaves `errorKind` unset — it is never invented.

## 3. Progress, joined onto the rows

`recordProgress` / `getProgressSnapshot` shipped with the transfer-progress
release. `selectEntries` now takes the snapshot as an optional second argument
and joins each tick onto its row by the same `${source}:${id}` key:

```ts
selectEntries(bridge.getSnapshot(), bridge.getProgressSnapshot())
```

Progress stays a **separate store**, deliberately. Ticks arrive orders of
magnitude more often than lifecycle events; routing them through the ring buffer
would evict a whole session's history within one large upload, and copy a
500-element array per tick. Each call keeps exactly one entry, replaced in place
and released the moment the call concludes — which is what keeps the map bounded
over a long session.

The argument is optional, so a panel that draws no progress bars passes nothing
and behaves exactly as before.

## API additions

| Addition                                  |                                             |
| ----------------------------------------- | ------------------------------------------- |
| `InspectorEvent.transport?: string`       | the wire, on the event that opened the call |
| `InspectorEntry.transport?: string`       | hoisted onto the row                        |
| `InspectorEntry.errorKind?: string`       | the normalized failure classification       |
| `selectEntries(events, progress?)`        | second argument joins live transfers        |
| `TypeFetchErrorLike`                      | typefetch's error shape, structurally       |
| `TypeFetchRequestEvent` `start.transport` | the mirror gained the field typefetch emits |

## Backward compatibility

Nothing was renamed and nothing was removed. Every addition is optional:

- An existing panel reading `source`, `label` and `status` renders exactly as
  before — the new fields are simply ignored.
- `selectEntries(events)` with one argument still works; rows carry no
  `progress`.
- Overrides, correlation keys and the ring buffer are untouched.
- A client that reports no transport still produces complete rows.

The one thing to know if you were reading `source` as "the wire": it never was,
and now there is a field that is. See §1.
