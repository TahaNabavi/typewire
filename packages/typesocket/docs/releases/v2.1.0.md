# TypeSocket Contract-Linked Permissions

This release adds one small, **additive** field to the contract: an optional
`permission` requirement on a `client->server` event. It lets you declare *who
may emit an event* in the same place you declare its direction and schemas — the
rule is written **once** and read by both ends.

Fully backward compatible: an event without a `permission` key behaves exactly as
before, and typesocket gains **no new runtime dependency**.

## The `permission` key

Only `client->server` events carry it — **the client authorizes what it sends,
never what it receives.** Gating an inbound (`server->client`) frame is the
server's job at emit time, so there is no `permission` field there.

```ts
export const contracts = defineSocketContracts({
  chat: {
    deleteAny: {
      direction: "client->server",
      permission: { require: ["chat.MANAGE_MESSAGES"] }, // ← new
      request: z.object({ id: z.string() }),
      ack: z.object({ ok: z.boolean() }),
    },
  },
});
```

The value is a `PermissionRequirement`:

```ts
type PermissionRequirement = {
  require?: readonly string[]; // must hold ALL of these flags (hasAll)
  any?: readonly string[];     // must hold AT LEAST ONE (hasAny)
  reason?: string;             // human message for a guard / audit log
};
```

The flag names reference a
[`@tahanabavi/type-permission`](https://www.npmjs.com/package/@tahanabavi/type-permission)
bit map. As with typefetch's `EndpointDef.permission`, the type is **redeclared
structurally** rather than imported, so `P.authorize(perms, def.permission)`
type-checks with no adapter and typesocket stays schema-only.

## Reading it — both ends, one declaration

**Server.** A Socket.IO gateway guard reads `def.permission` for the incoming
event and rejects the frame (or its ack) when the actor's bitfield lacks the
required flags:

```ts
import { P } from "./permissions";

const decision = P.authorize(socket.data.perms, def.permission);
if (!decision.granted) {
  return ack?.({ error: { code: "FORBIDDEN", missing: decision.missing } });
}
```

**Client.** Register `createPermissionMiddleware` via the new `authorizeOutbound`
option — a denied emit then throws before it reaches the wire:

```ts
import { SocketClient, createPermissionMiddleware } from "@tahanabavi/typesocket";
import { P } from "./permissions";

const client = new SocketClient(config, contracts, {
  authorizeOutbound: createPermissionMiddleware({
    getPermissions: () => store.getSnapshot().global, // synchronous
    authorize: P.authorize,
  }),
});

await client.modules.chat.deleteAny({ id }); // throws PermissionDeniedError if denied
```

It goes through `authorizeOutbound`, not `client.use()`, on purpose: a
`SocketMiddleware` can only *drop* a frame silently (its throws are swallowed),
whereas the guard must **throw to the call site** — an ack'd emit rejects, a
fire-and-forget one throws synchronously. That's also why `getPermissions` is
synchronous: a `void` emit resolves synchronously, so the check must too. Prefer
an inline check? Every emit member still exposes `.def.permission`.

The client check is **UX only** — the server re-authorizes every frame from the
session, so a stale client bitfield can never grant access.

## API additions

| Export                          | Kind  | Purpose                                                       |
| ------------------------------- | ----- | ------------------------------------------------------------ |
| `ClientToServerDef.permission`  | field | Optional `PermissionRequirement` on a `client->server` event. |
| `PermissionRequirement`         | type  | `{ require?, any?, reason? }` — redeclared structurally.      |
| `createPermissionMiddleware`    | function | Builds the pre-emit guard that enforces the `permission` key. |
| `PermissionDeniedError`         | class | Thrown by the guard when an emit is blocked.                 |
| `authorizeOutbound` option / `OutboundAuthorizer` | option / type | Registers a throwing pre-emit guard on the client. |
| `client.setOutboundAuthorizer()` | method | Set/replace the guard after construction.                  |

## Backward compatibility

* The `permission` key is optional and only valid on `client->server` events.
  Events without it are unchanged.
* No new dependency: the type is structural. Nothing is imported at runtime.
* Emitting, listening, acks, middleware, and instrumentation are all untouched.
