# v0.1.0 — gRPC without a protobuf runtime

`@tahanabavi/typefetch-grpc` makes a gRPC method an ordinary route in a
typefetch contract — the same client, middleware chain, `onError`, retry policy,
mock mode and devtools timeline as every other endpoint.

Its defining constraint: **nothing published here depends on protobuf.** A
protobuf runtime plus generated stubs is a large, permanent cost, and most teams
reaching for gRPC-from-the-browser are already behind a Connect or grpc-web
proxy that speaks JSON perfectly well.

---

## 1. Connect unary JSON is the default

```ts
syncUser: {
  transport: "grpc",
  service: "user.v1.UserService",
  rpc: "SyncUser",
  request: z.object({ id: z.string() }),
  response: User,
}
```

sends `POST /user.v1.UserService/SyncUser` with a JSON body. That is the whole
wire format: the URL _is_ the routing, the body is the message, the status is
the status.

Which means it is **curl-able**, readable in a browser network tab, and
debuggable by anyone who has never heard of gRPC:

```bash
curl -X POST https://api.example.com/user.v1.UserService/SyncUser \
  -H 'Content-Type: application/json' \
  -H 'Connect-Protocol-Version: 1' \
  -d '{"id":"1"}'
```

`Connect-Protocol-Version: 1` is sent on every request — Connect servers in
strict mode reject requests without it, and the failure is otherwise opaque.

## 2. Binary grpc-web behind a codec seam

When you do need binary, the adapter owns framing and trailers; the **codec**
owns message bytes:

```ts
export interface GrpcCodec {
  encode(input: unknown): Uint8Array
  decode(bytes: Uint8Array): unknown
  contentType?: string
}
```

Supply one per endpoint or per client and the transport switches to
length-prefixed frames. That split is why protobuf never enters anything this
repo publishes: the dependency lives in _your_ codec, built from _your_ `.proto`
files, and only for the routes that need it.

The framing is implemented here in full — the 5-byte prefix (1 flag byte, 4-byte
big-endian length), the `0x80` trailer flag, and trailer parsing including
percent-decoded `grpc-message`.

## 3. Errors normalize, in both directions

The gRPC status set is the canonical vocabulary for typefetch's `ErrorKind`, so
this package carries the mapping the rest of the family reads:

| gRPC                   | HTTP | `ErrorKind`          |
| ---------------------- | ---- | -------------------- |
| `5 NOT_FOUND`          | 404  | `not_found`          |
| `7 PERMISSION_DENIED`  | 403  | `permission_denied`  |
| `16 UNAUTHENTICATED`   | 401  | `unauthenticated`    |
| `3 INVALID_ARGUMENT`   | 400  | `invalid_argument`   |
| `4 DEADLINE_EXCEEDED`  | 504  | `deadline_exceeded`  |
| `8 RESOURCE_EXHAUSTED` | 429  | `resource_exhausted` |
| `14 UNAVAILABLE`       | 503  | `unavailable`        |

Both directions are implemented and tested: code → kind, code → HTTP status, and
HTTP status → code for the proxies and gateways that answer before the service
does.

**`errors` maps are keyed by the numeric gRPC code**, not the HTTP status:

```ts
errors: { 5: z.object({ message: z.string() }) }
```

That keeps a route's declared errors meaning the same thing whether the call
went over Connect (real statuses) or binary grpc-web (always 200 plus a
trailer).

## 4. The trailer problem, named

grpc-web answers `200 OK` for _every_ outcome and reports the real one in a
trailer. So a `NOT_FOUND` can only be detected while decoding a success — the
adapter throws a `RichError` from `decode`, putting it on the client's normal
failure path.

When the trailer is missing entirely, the error says why:

> gRPC response ended without a trailer. If this is a browser and the server is
> cross-origin, it most likely did not expose the trailer via
> `Access-Control-Expose-Headers: grpc-status, grpc-message`.

That specific CORS misconfiguration is the single most common way a working
grpc-web setup fails in a browser and nowhere else, and it produces no useful
error anywhere in the stack. Naming it is worth more than the rest of the error
handling combined.

## 5. Deadlines

```ts
deadlineMs: 5000
```

Sends both spellings — `Connect-Timeout-Ms` and `grpc-timeout` — because Connect
servers read the first and grpc-web proxies the second, and sending both costs
nothing.

## 6. API

| Export                                                                 | Purpose                                                |
| ---------------------------------------------------------------------- | ------------------------------------------------------ |
| `grpcTransport(config?)`                                               | The adapter. Pass to `transports` at the setup site.   |
| `GrpcCode`                                                             | The status enum                                        |
| `codeName` · `parseCode`                                               | Name ↔ code, accepting both `canceled` and `cancelled` |
| `kindFromGrpcCode` · `statusFromGrpcCode` · `codeFromHttpStatus`       | The mappings, standalone                               |
| `encodeFrame` · `decodeFrames` · `parseTrailer` · `trailerFromHeaders` | grpc-web framing                                       |
| `GrpcCodec`                                                            | The binary seam                                        |

## 7. Contract fields

| Field               | Meaning                                     |
| ------------------- | ------------------------------------------- |
| `transport: "grpc"` | selects this adapter                        |
| `service`           | fully-qualified, e.g. `user.v1.UserService` |
| `rpc`               | the method name                             |
| `deadlineMs`        | per-route deadline                          |
| `codec`             | per-route binary codec                      |

Missing `service` or `rpc` is caught at `init()`, naming the endpoint — not at
the first call in production.

## 8. Backward compatibility

First release; nothing to break. Zero runtime dependencies, asserted in CI —
which for this package is the entire point, since the obvious implementation
would have added a protobuf runtime to every consumer.

## 9. Deliberately out of scope

- **Streaming.** Unary only. Server-streaming over Connect is real and useful,
  but it is a different response contract (`AsyncIterable`, not a value), and
  bolting it onto `response: z.object(…)` would be a lie.
- **Codegen from `.proto`.** A `typewire import --from proto` command belongs in
  the CLI, not in a runtime transport.
- **A bundled protobuf codec.** That is the dependency this design exists to
  avoid. A separate opt-in package is the right home.

## 10. What is not proven yet

Connect ships a **conformance runner**, and this package does not run it. That
is a real gap, and it is recorded rather than glossed: the harness drives a
client under test over length-prefixed **protobuf** on stdin/stdout, so speaking
it needs exactly the runtime the codec seam exists to avoid shipping.

The right shape is a CI-only harness with `@bufbuild/protobuf` as a _dev_
dependency — dev deps do not ship, so the guarantee holds. Until that exists,
what is proven is the 36 tests here: URL shape, protocol-version header, both
deadline spellings, code↔status↔kind in both directions, framing, trailers,
trailers-only responses, and the CORS-hidden-trailer case.

Writing a workflow that _claimed_ conformance without running it would be worse
than the honest gap.
