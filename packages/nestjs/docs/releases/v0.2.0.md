# TypeWire NestJS — Permission Guard

This release adds server-side enforcement for the contract-linked `permission`
key introduced in [`typefetch` v1.8.0](../../../typefetch/docs/releases/v1.8.0.md):
a NestJS guard that reads an endpoint's requirement off its contract and rejects
unauthorized requests with a typed `403`, reusing the exact
[`@tahanabavi/type-permission`](https://www.npmjs.com/package/@tahanabavi/type-permission)
bit map the frontend checks.

Fully additive: routes without a requirement are never blocked, and the package
still depends only on typefetch.

## `createPermissionGuard(config)`

You supply two functions; the factory returns a guard class.

```ts
import { APP_GUARD } from "@nestjs/core";
import { createPermissionGuard } from "@tahanabavi/typewire-nestjs";
import { P } from "./permissions";

export const PermissionGuard = createPermissionGuard({
  getPermissions: (req) => req.user.perms as bigint,   // may be async
  authorize: P.authorize,                              // from type-permission
  onDeny: ({ decision, context }) =>                   // audit-log seam
    logger.warn("denied", { missing: decision.missing }),
});

@Module({ providers: [{ provide: APP_GUARD, useClass: PermissionGuard }] })
export class AppModule {}
```

| Config field     | Required | Purpose                                                                 |
| ---------------- | :------: | ----------------------------------------------------------------------- |
| `getPermissions` |    ✓     | Read the actor's `bigint` bitfield off the request. Sync or async.      |
| `authorize`      |    ✓     | Evaluate a requirement → decision. Pass `P.authorize`.                  |
| `onDeny`         |          | Called on every denial before the 403 — log it in production.           |
| `onForbidden`    |          | Build a custom thrown exception instead of the default `ForbiddenException`. |

**Authentication is assumed to have happened upstream** — this guard only
*authorizes*. Register it after your auth guard (or inside the same chain).

## How the requirement is resolved

For each request the guard looks for a requirement in this order:

1. `@RequirePermission()` metadata on the **handler**, then the **class**.
2. The bound contract endpoint's `permission` key
   (`@TypeFetchEndpoint(contract)`).

The first match wins, so `@RequirePermission` **overrides** a contract's
`permission` on a specific route. If neither is present, the route passes
untouched — enforcement is opt-in per route.

## The 403 body

The default `ForbiddenException` names what was missing, so a client can render a
precise message or refetch its permissions:

```jsonc
{
  "statusCode": 403,
  "code": "FORBIDDEN",
  "message": "Insufficient permissions", // or the requirement's `reason`
  "missing": ["chat.MANAGE_MESSAGES"],    // from `require`
  "missingAny": ["post.publish"]          // from `any`, when that was the failing side
}
```

## `@RequirePermission(requirement)`

For routes with no contract, or to override one:

```ts
@Post("ban")
@RequirePermission({ require: ["guild.KICK_MEMBERS"] })
banUser() { /* ... */ }

@RequirePermission({ any: ["post.publish", "post.moderate"] })
publish() { /* ... */ }
```

`requirement` is a `PermissionRequirement` — `{ require?, any?, reason? }`.

## Dependency boundary

The guard's `authorize` is typed against `PermissionDecisionLike`
(`{ granted, missing?, missingAny?, reason? }`), declared **structurally** so this
package keeps depending only on typefetch. `type-permission`'s `AuthorizeDecision`
satisfies it, so `P.authorize` is passed straight through with no adapter — the
same seam typefetch and typesocket use for the `permission` field itself.

## API additions

| Export                    | Kind      | Purpose                                                       |
| ------------------------- | --------- | ------------------------------------------------------------ |
| `createPermissionGuard`   | function  | Build the guard from `{ getPermissions, authorize, onDeny?, onForbidden? }`. |
| `RequirePermission`       | decorator | Declare/override a route's requirement.                      |
| `PermissionGuardConfig`   | type      | The factory config shape.                                    |
| `PermissionDecisionLike`  | type      | The structural decision shape `authorize` returns.           |
| `TYPEFETCH_PERMISSION_METADATA` | constant | Metadata key for `@RequirePermission`.                  |

## Backward compatibility

* Nothing is enforced until you register the guard. Existing apps are unaffected.
* No new dependency — the type surface is structural.
* Validation, envelopes, encryption, Swagger, and the existing decorators are all
  unchanged.
