# v0.2.0 — one contract file, every wire

`@tahanabavi/typewire-nestjs` bound NestJS routes to typefetch contracts. Then
typefetch v2 made the transport pluggable, and a contract file stopped being a
list of HTTP routes: one client now speaks REST, GraphQL and gRPC, and
typesocket speaks a fourth wire beside it.

The server half had not moved. This release moves it — and adds the
contract-linked permission guard, which had not shipped either.

Nothing about an existing HTTP route changes. Every addition is a new decorator
behind a new entry point, so an app that serves REST installs nothing extra and
its handlers are untouched.

---

## 1. Each wire, bound by its own decorator

```ts
@TypeFetchEndpoint(contracts.user.getUser)     // http    — unchanged
@GrpcEndpoint(contracts.user.syncUser)         // grpc    — .../grpc
@GraphQLEndpoint(contracts.user.profile)       // graphql — .../graphql
@SocketEvent(events.chat.sendMessage)          // ws      — .../socket
```

Four decorators rather than one dispatching decorator, on purpose. It mirrors
the client, where a transport adapter is _registered_ explicitly at the setup
site rather than discovered — and if the server could silently serve a transport
the client never registered, the two halves of one contract could disagree about
which wire they are on.

Each entry point carries its own optional peer dependency, so an HTTP-only app
never installs a package it does not use. That costs nothing: the peer for each
wire is what augments typefetch's `TransportRegistry` in the first place, so
without it the contract could not have been written.

**The mismatch fails at bootstrap.** `@TypeFetchEndpoint()` previously read
`endpoint.method` off a gRPC contract, found `undefined`, and threw
`Unsupported HTTP method "undefined"` — the symptom, not the cause. Now:

```txt
[typewire-nestjs] @TypeFetchEndpoint() serves "http" endpoints, but
user.v1.UserService/GetUser is declared for "grpc". Bind it with
`@GrpcEndpoint()` from "@tahanabavi/typewire-nestjs/grpc" instead.
```

Two internal rules make that possible, and both are exported because user-land
guards need them too. `transportOf(endpoint)` reads the wire (absent means
HTTP, which is what keeps pre-v2 contracts meaning what they did), and
`describeContractRoute(endpoint)` names a route **without reading a field the
transport may not have** — the same discipline the client's `describe()` seam
enforces.

## 2. gRPC — Connect JSON, no protobuf

`@GrpcEndpoint()` serves the wire `@tahanabavi/typefetch-grpc` speaks by
default: `POST /<service>/<rpc>`, the message as the JSON body, real HTTP
statuses. That is an HTTP route, which is why a NestJS app can serve gRPC
contracts with **no protobuf runtime, no `.proto` file and no code generation**.

Because it is a route, everything else already worked: guards (including the
permission guard below), interceptors, request validation, response validation.
What had to be built is the part that is gRPC's rather than HTTP's.

**Failures are named in the gRPC key space.** A gRPC endpoint's `errors` map is
keyed by status code, not HTTP status — that is what makes a declared error mean
the same thing over Connect and over binary grpc-web. Throw `GrpcException` to
name a code, or throw the NestJS exception you already would:

```ts
if (!user) throw new GrpcException(GrpcCode.NotFound, `No user ${input.id}`)
if (!user) throw new NotFoundException('No such user') // → not_found, 404
```

The status→code table here is deliberately **not** the client's
`codeFromHttpStatus`. There, a 404 came from something that never reached the
RPC, so it means "no such method" — `unimplemented`. Here it came from a handler
that looked and did not find, which is `not_found`. Same input, opposite
meaning, because the thrower is different.

**Deadlines are enforced.** The client sends the contract's `deadlineMs` as
`Connect-Timeout-Ms` and `grpc-timeout`. A deadline only the client honours is
just a timeout: the caller gives up and the server keeps the database
connection. `ConnectDeadlineInterceptor` cuts the handler off at the deadline
and answers `deadline_exceeded` / `504`; `@GrpcDeadline()` hands the handler the
`AbortSignal` so the work itself can stop.

Both spellings are read, and the case matters: in `grpc-timeout`, `M` is minutes
and `m` is milliseconds — reading them the wrong way round is a 60000× error in
the direction that hangs a server.

Two smaller things: a unary call answers **200**, not Nest's default 201 for a
POST (a status saying "created" for every read is a lie a cache may act on); and
the response envelope is never applied, because a Connect client reading
`{ success: false, message }` sees no `code` and classifies every failure as
`unknown`.

## 3. GraphQL — no GraphQL runtime

`ContractGraphQLModule.forRoot({ contracts })` mounts one endpoint;
`@GraphQLEndpoint()` marks the resolvers, which are ordinary NestJS providers
discovered at bootstrap.

There is **no `graphql` package, no SDL and no resolver map**, and that is a
consequence of what the client already does: `@tahanabavi/typefetch-graphql`
generates its operation document _from the endpoint's Zod `response` schema_. So
both halves agree on the selection set by construction — an operation can be
addressed by name and answered from the same schema that asked for it.

Three decisions inside are worth naming.

**`contracts` is required.** A GraphQL operation is addressed by name, and the
name the client sends is derived from the endpoint's `"module.endpoint"` id
(`user.profile` → `UserProfile`). An endpoint object on its own does not know
its own id, so the map it came from is the only place that name exists. The
derivation itself is imported from the client's transport package rather than
restated — a second copy of that rule would be a routing table that drifts
silently.

**Resolvers run through NestJS's own pipeline**, via `ExternalContextCreator` —
the same mechanism `@nestjs/graphql` uses. That is what makes
`@UseGuards(PermissionGuard)` enforce a contract's `permission` key in a
resolver exactly as it does on a route, and what makes `@ContractInput()` return
the validated variables. Nest's _route_ parameter decorators are refused at
bootstrap instead: `@Body()` in a resolver reads the GraphQL envelope
(`{ query, variables }`) rather than the operation's variables, which is a bug
that surfaces as a validation failure three layers away.

**Media type negotiation is honoured.** A client accepting
`application/graphql-response+json` gets the real HTTP status on a failure. One
accepting only `application/json` gets the spec's `200` with the intended status
in `extensions.http.status` — the only place a status can live on that media
type, and what typefetch reads.

Queries may be sent over `GET` so a CDN can cache them; mutations are refused
over GET, because a mutation a cache can replay is a way to lose a write.

### What this is not

**The document is not executed.** The operation is resolved by name and the
response is the endpoint's `response` schema — which is exactly what the
client's generated selection set asked for, and is therefore correct for any
client generated from the same contract.

It is not a general GraphQL server: no introspection, no schema stitching, no
field-level resolvers, no aliases, no fragments. A hand-written query selecting
a subset gets the full contract shape back (harmless — the client's schema
strips it); one using an alias will not resolve. `@nestjs/graphql` is the right
tool for those, and this does not try to replace it.

## 4. typesocket gateways

The README had said "typesocket gateways planned" since 0.1.0. They are here.

```ts
export const events = bindSocketContracts(wsContracts);

@SocketEvent(events.chat.sendMessage)
async send(@SocketPayload() input: InferSocketRequest<typeof events.chat.sendMessage>) {
  const message = await this.chat.post(input.text);
  this.emit(events.chat.message, message);   // validated against `payload`
  return { id: message.id };                 // validated against `ack`
}
```

One contract object serves both ends, which is what typesocket's `direction`
field was for: the client emits `client->server` and listens to
`server->client`, and a gateway does the reverse from the same file.

`bindSocketContracts()` exists because a definition object does not know its own
name — the wire event name defaults to `"module.event"`, a fact about where it
sits in the map. Binding resolves it once, the same way the client does, and
refuses two events colliding on one wire name, where a single frame would reach
both handlers and both would try to acknowledge it.

Three checks, one per direction that can break:

| Checked         | Against   | Why                                                                                                                              |
| --------------- | --------- | -------------------------------------------------------------------------------------------------------------------------------- |
| inbound frame   | `request` | via `@SocketPayload()` — nothing else validates what a sender put on the wire                                                    |
| acknowledgement | `ack`     | typesocket **validates the ack on arrival**, so a drifted one rejects far from the server that produced it                       |
| server push     | `payload` | typesocket **drops** an inbound payload that fails its schema — a renamed field turns into a listener that silently stops firing |

`createSocketPermissionGuard()` enforces a `client->server` event's contract
`permission` server-side. typesocket ships a client-side equivalent and says of
it, in its own docs, that the check is UX only and a gateway guard is the real
enforcement point. This is that point, reading the same requirement off the same
contract with the same bit map.

**An ack is not an error channel.** A rejected frame throws
`SocketContractException`, which NestJS sends as socket.io's standard
`exception` event, and the frame is not acknowledged. Putting an error object in
the ack instead would arrive as a _malformed ack_ — typesocket validates it
against the contract's `ack` schema — rather than as the rejection it is. An
event whose failures the caller must handle should say so in its contract:
`ack: z.discriminatedUnion("ok", [ … ])`, the same rule that governs `errors` on
an HTTP endpoint.

## 5. Non-JSON responses actually work

An HTTP contract could always declare `responseType: "file"` with `zFile()`.
Serving one did not work: the handler's `Buffer` was JSON-serialised into
`{"type":"Buffer","data":[37,80,…]}`, and before that the response validator
rejected it — `zFile()` describes a `{ blob, filename, … }`, a value that only
exists after the _client_ decodes the body.

Both halves are fixed:

- `contractFile(body, { filename, contentType })` — or a bare `Buffer` /
  `Readable` — is streamed rather than serialised.
- `Content-Disposition` is sent in both RFC 6266 spellings, so a non-ASCII name
  survives and the ASCII fallback cannot inject a header parameter of its own.
- `Content-Length` is sent whenever it is known, which is what makes the
  client's download progress report a percentage instead of an indeterminate
  spinner.
- `Access-Control-Expose-Headers` gains both, appended rather than replaced.
  Cross-origin they are invisible by default, and `CONTRACT_EXPOSED_HEADERS` is
  exported for the CORS config, which is the only place they can be _granted_.
- Response validation is skipped for the types it cannot check, and a handler
  returning the wrong kind of thing is caught with a message naming the fix.
- `responseType: "text"` is sent as `text/plain`, not Express's `text/html` —
  wrong for a CSV, and a stored-XSS foot-gun when the string came from a user.

The contract's `driver` (`"auto"` / `"fetch"` / `"xhr"`) needs nothing
server-side: both produce the same HTTP request. The two headers above are what
they actually depend on.

## 6. The envelope learned what it does not own

`TypeFetchModule.forRoot({ envelope: true })` registers an app-wide interceptor
and filter. With three more wires in the app that became a correctness problem,
not a preference: a `{ success, data }` wrapper around a Connect error body, a
GraphQL `{ data }`, or a WebSocket ack is a payload no client on that wire can
read.

The envelope now exempts, automatically: anything that is not an HTTP call, and
any route bound to a non-HTTP contract. `@SkipEnvelope()` is the manual form,
for a health check a load balancer parses or a webhook receipt whose shape
belongs to someone else. It covers the error branch too — a route answering
`{ status }` on 200 and `{ success: false }` on 404 has two shapes to handle,
which is the thing the exemption exists to avoid.

The catch-all filter also rethrows on a non-HTTP context instead of trying to
`reply()` to a socket, which is what an app-wide HTTP filter has to do in any
mixed application.

## 7. Permission guard

Where `auth` answers _"is there a token?"_, this answers _"is this actor
allowed?"_ — enforcing the optional `permission` key an endpoint declares on its
contract, using the same [`@tahanabavi/type-permission`](../../../permission)
bit map the frontend checks. The route cannot drift from the button.

```ts
export const PermissionGuard = createPermissionGuard({
  getPermissions: (req) => req.user.perms as bigint, // may be async
  authorize: P.authorize, // from type-permission
  onDeny: ({ decision, context }) =>
    // audit-log seam
    logger.warn('denied', { missing: decision.missing }),
})

@Module({ providers: [{ provide: APP_GUARD, useClass: PermissionGuard }] })
export class AppModule {}
```

Authentication is assumed to have happened upstream; this guard only
_authorizes_. For each request the requirement is resolved from
`@RequirePermission()` metadata (handler, then class), falling back to the bound
contract endpoint's `permission`. The first match wins, so `@RequirePermission`
overrides a contract on a specific route, and a route with neither always
passes — enforcement is opt-in per route.

The default `ForbiddenException` names what was missing, so a client can render
a precise message or refetch its permissions:

```jsonc
{
  "statusCode": 403,
  "code": "FORBIDDEN",
  "message": "Insufficient permissions", // or the requirement's `reason`
  "missing": ["chat.MANAGE_MESSAGES"], // from `require`
  "missingAny": ["post.publish"], // from `any`, when that was the failing side
}
```

`authorize` is typed against `PermissionDecisionLike`
(`{ granted, missing?, missingAny?, reason? }`), declared **structurally** so
this package keeps depending only on typefetch — `type-permission`'s
`AuthorizeDecision` satisfies it, so `P.authorize` passes straight through with
no adapter. The same seam typefetch and typesocket use for the `permission`
field itself.

It now works on all four wires: as a guard on an HTTP route, on a gRPC route, on
a GraphQL resolver (guards run there, see §3), and — as
`createSocketPermissionGuard()` — on a gateway handler.

## Backward compatibility

Nothing was renamed and nothing was removed.

- **Every existing HTTP route behaves identically.** `@TypeFetchEndpoint()`,
  `@UseContract()`, the `@Contract*()` decorators, validation, coercion,
  form-data uploads, encryption and Swagger are untouched.
- `InferRequest` / `InferResponse` / `ContractHandler` accept an endpoint on any
  transport now instead of only HTTP. Widening a constraint breaks nothing.
- `UseContract()` accepts any transport, for the same reason — it declares no
  route, so it composes with one you wrote yourself on any wire.
- `getContractEndpoint()` returns `AnyEndpointDefZ`. Reading `.method` or
  `.path` off it now needs a narrowing check **if** a transport package is
  installed, because those fields do not exist on every variant — the same
  narrowing typefetch's own `MiddlewareContext.endpoint` requires.
- `validateRequest()` takes any transport and, for a non-HTTP one, treats the
  whole request as the message: the `{ path, query, body }` split is an HTTP
  convention. Issue paths on those wires lose the `body.` prefix, which named a
  part of the request that does not exist there.
- The response envelope now exempts non-HTTP contexts and non-HTTP contract
  routes. This is a behaviour change, and only for cases that could not have
  worked before.
- `buildOpenApiDocument()` skips non-HTTP endpoints rather than throwing on the
  missing `path`. OpenAPI describes HTTP; a mixed contract documents its HTTP
  half and leaves the rest to each wire's own schema language.

## Not served

Stated rather than implied, because a silent gap is worse than a named one:

- **Binary grpc-web.** An endpoint with a `codec` is refused at bootstrap. It
  needs raw-body access and length-prefixed trailer framing on the way out; put
  a grpc-web proxy in front, or use Connect JSON on both ends.
- **A general GraphQL server.** See §3 — no introspection, aliases or fragments.
- **Field-level encryption on GraphQL.** The `encryption` config is honoured on
  HTTP and gRPC — both go through the contract interceptor — and is _not_
  applied on the GraphQL transport. The client's `encryptionMiddleware` does run
  there, so the registry logs a warning naming the endpoint at bootstrap rather
  than letting ciphertext reach a resolver that never decrypts it. typesocket
  contracts have no encryption key at all.
- **GraphQL request batching.** One operation per request.
