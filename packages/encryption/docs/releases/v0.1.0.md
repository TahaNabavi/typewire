# v0.1.0 — encryption leaves the core

`@tahanabavi/typefetch-encryption` is the field-level encryption middleware,
extracted from `@tahanabavi/typefetch` unchanged.

The move is the release. `crypto-js` and `node-forge` were runtime dependencies
of the core — which meant **every** consumer of a typed HTTP client installed two
crypto libraries, and shipped them, whether or not a single field was ever
encrypted. Together with `jiti` leaving alongside the CLI, this is what makes
typefetch's "zero runtime dependencies" true rather than aspirational, and it is
among the first things an enterprise audit checks.

---

## 1. What it does

Encrypt named fields on the way out and decrypt them on the way back, without
the call site or the contract knowing:

```ts
import { encryptionMiddleware } from "@tahanabavi/typefetch-encryption";

client.use(
  encryptionMiddleware({
    method: "aes",
    secret: process.env.PAYLOAD_KEY!,
  }),
);
```

Selection is per field, declared as a shape mirroring the payload, so nothing is
encrypted by accident:

```ts
{ body: { ssn: true, card: { number: true } } }
```

| Method | Notes |
| --- | --- |
| `aes` | `crypto-js` AES |
| `des` · `tripledes` | legacy interop |
| `rabbit` · `rc4` | legacy interop |
| `base64` | **encoding, not encryption** — for transport-safety only |
| `rsa` | `node-forge`, public-key |
| `custom` | your own `encrypt`/`decrypt` pair |

`base64` is listed as a method because the shape is identical, not because it
protects anything. It is labelled that way in the types and the README so nobody
reaches for it expecting confidentiality.

## 2. The migration

One import path changes:

```diff
- import { encryptionMiddleware } from "@tahanabavi/typefetch";
+ import { encryptionMiddleware } from "@tahanabavi/typefetch-encryption";
```

```bash
npm i @tahanabavi/typefetch-encryption
```

**The types did not move.** `EncryptionMethod`, `DeepEncryptionMap` and
`EncryptionConfig` still live in the core, because they are pure types with no
runtime cost — so a contract that *declares* encryption stays declarable without
installing this package. Only the implementation moved.

Behaviour is byte-for-byte identical: the middleware, its options and its tests
came across unchanged, and the tests are the same ten that guarded it in the
core.

## 3. Backward compatibility

The import path is the only break, and it is a compile error rather than a
silent behaviour change — which is the right kind of break. It is recorded
against the migration codemod planned as `@tahanabavi/typewire-codemod`.

Everything else — the option shape, the field-selection map, the supported
methods, the ordering relative to other middleware — is unchanged.

## 4. Dependencies

`crypto-js` and `node-forge`, and nothing else. These are pinned in
`scripts/assert-no-deps.mjs`, so adding a third fails CI rather than passing
review: the whole point of this package existing is that its dependencies are
paid for only by the people who use it.

## 5. Deliberately out of scope

- **Key management.** Rotation, derivation and storage are the application's
  problem, and a middleware that guessed at them would be worse than one that
  does not try.
- **Transport-level encryption.** That is TLS. This is for fields that must stay
  opaque to something that legitimately terminates TLS — a proxy, a log
  aggregator, a support tool.
- **Encrypting whole payloads by default.** Explicit field selection is the
  design: encrypting everything defeats server-side validation, indexing and
  every meaningful error message.
