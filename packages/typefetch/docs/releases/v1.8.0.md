# TypeFetch Contract-Linked Permissions

This release adds one small, **additive** field to the contract: an optional
`permission` requirement on an endpoint. It lets you declare *who may call an
endpoint* in the same place you already declare its method, path, and schemas —
so the rule is written **once** and read by both ends.

Fully backward compatible: an endpoint without a `permission` key behaves
**byte-for-byte** as before, and TypeFetch gains **no new runtime dependency**.

## The `permission` key

```ts
export const contracts = {
  message: {
    remove: {
      method: "DELETE",
      path: "/messages/:id",
      permission: { require: ["chat.MANAGE_MESSAGES"] }, // ← new
      request: z.object({ path: z.object({ id: z.string() }) }),
      response: z.object({ removed: z.string() }),
    },
  },
} as const;
```

The value is a `PermissionRequirement`:

```ts
type PermissionRequirement = {
  require?: readonly string[]; // must hold ALL of these flags (hasAll)
  any?: readonly string[];     // must hold AT LEAST ONE (hasAny)
  reason?: string;             // human message for the 403 body / audit log
};
```

When both `require` and `any` are present, **both** conditions must pass. The
flag names (`"chat.MANAGE_MESSAGES"`, …) reference a
[`@tahanabavi/type-permission`](https://www.npmjs.com/package/@tahanabavi/type-permission)
bit map.

## Why it's dependency-free

`PermissionRequirement` is **redeclared structurally** in typefetch rather than
imported from `type-permission` — the same pattern `type-devtools-core` uses to
redeclare transport event types. The two declarations are structurally identical,
so:

```ts
import { P } from "./permissions";           // your type-permission bit map
P.authorize(perms, endpoint.permission);     // type-checks, no adapter
// → { granted: boolean; missing: string[]; missingAny?: string[]; reason?: string }
```

You only pull in `type-permission` where you actually evaluate permissions
(server guard, client pre-flight). TypeFetch itself stays schema-only.

## Reading it — both ends, one declaration

**Server.** [`@tahanabavi/typewire-nestjs`](https://www.npmjs.com/package/@tahanabavi/typewire-nestjs)
ships `createPermissionGuard({ getPermissions, authorize })`. It reads the
requirement off the contract metadata (`endpoint.permission`) and rejects with a
`403` whose body names the missing flags. A route with no requirement is never
blocked.

**Client.** Register `createPermissionMiddleware` once — the mirror of the server
guard — and every endpoint with a `permission` key is pre-blocked before the
request is sent:

```ts
import { createPermissionMiddleware } from "@tahanabavi/typefetch";
import { P } from "./permissions";

client.use(createPermissionMiddleware({
  getPermissions: () => store.getSnapshot().global, // cheap; runs per request
  authorize: P.authorize,
}));

await api.message.remove({ path: { id } }); // throws PermissionDeniedError if denied
```

It reads `ctx.endpoint.permission`, evaluates it with your injected `authorize`,
and throws `PermissionDeniedError` (`{ status: 403, missing, missingAny? }`) — so a
client-side block reads like the server's 403. Endpoints with no `permission` key
pass straight through. Prefer a one-off inline check? `endpoint.permission` is
still there to read directly.

Because the server recomputes from the session on every request, the client check
is **UX only** — a convenience, never the enforcement point.

## API additions

| Export                  | Kind  | Purpose                                                      |
| ----------------------- | ----- | ------------------------------------------------------------ |
| `EndpointDef.permission` | field | Optional `PermissionRequirement` on any endpoint.           |
| `PermissionRequirement` | type  | `{ require?, any?, reason? }` — redeclared structurally.     |
| `createPermissionMiddleware` | function | Client-side pre-block middleware enforcing the `permission` key. |
| `PermissionDeniedError` | class | Thrown by the middleware when a call is blocked (`status: 403`). |

## Backward compatibility

* The `permission` key is optional. Endpoints without it are unchanged, and the
  request path adds no work.
* No new dependency: the type is structural. Nothing is imported at runtime.
* All existing behavior — validation, middleware, retries, mock mode, typed
  errors, instrumentation — is untouched.
