# TypeFetch 2.0 — Pluggable Transports

TypeFetch spoke one wire: `fetch`, swapped for `XMLHttpRequest` when a request
asked for upload progress. This release makes the wire **pluggable**. gRPC and
GraphQL now ship as separate installable packages that feed the same contract,
the same middleware chain, the same `onError`, the same retry policy, the same
mock mode and the same devtools timeline.

The point is not that TypeFetch speaks three protocols. It is that **application
code stops caring which one it is on**. A team mid-migration from REST to gRPC
runs one client with one auth setup and one error shape, instead of three of
each.

It also makes a claim that was not previously true: `@tahanabavi/typefetch` has
**zero runtime dependencies**. `crypto-js`, `node-forge` and `jiti` have moved to
the packages that actually need them.

---

## 1. Why this was cheap

gRPC-for-the-web (Connect, grpc-web) and GraphQL-over-HTTP are both **a POST with
a body**. Neither needs a new socket, a new client, or a second pipeline. Only
four things vary per wire, and they are the entire adapter interface:

1. build `url` + `RequestInit` from the parsed input,
2. decode a 2xx body into the value `response` validates,
3. turn a failure into a normalized error,
4. describe itself to tooling.

Everything else — retry, `auth` + `tokenProvider`, `timeout`, `AbortSignal`,
mock mode, forced mocks, `instrument()` events and overrides, the middleware
chain — is transport-independent and did not move.

Notably, **`endpointId` did not change**, so `query-core`, `devtools-core`,
`react` and `devtools` needed no changes at all. They key on the id, and the id
is the same.

## 2. The contract type is now open

A closed union (`"http" | "grpc" | "graphql"`) cannot work when adapters live
outside the core: the core would have to know `service`/`rpc` fields that ship in
a package it must never import. So the endpoint type is built from an
**augmentable registry**:

```ts
// core
export interface TransportRegistry {
  http: {
    method: Method;
    path: string;
    bodyType?: "json" | "form-data";
    responseType?: ResponseType;
  };
}
```

A transport package merges its variant in:

```ts
// @tahanabavi/typefetch-grpc
declare module "@tahanabavi/typefetch" {
  interface TransportRegistry {
    grpc: { service: string; rpc: string; deadlineMs?: number; codec?: GrpcCodec };
  }
}
```

**Installing the package is what adds the type.** `transport: "grpc"` does not
compile until `@tahanabavi/typefetch-grpc` is a dependency, and once it is, the
route is fully checked — including that a gRPC route may not carry `path`.

Routes with no `transport` key default to `"http"`, which is why every existing
contract compiles unchanged.

```ts
// http — exactly as before
getUser: { method: "GET", path: "/users/:id", request, response }

// grpc
getUser: { transport: "grpc", service: "user.v1.UserService", rpc: "GetUser",
           request, response, deadlineMs: 5_000 }

// graphql
getUser: { transport: "graphql", operation: "query", root: "user",
           request: z.object({ id: z.string() }), response: User }
```

## 3. Registering a transport

Explicit, at the setup site — so a REST-only app never ships a byte of a
transport it does not use:

```ts
import { ApiClient } from "@tahanabavi/typefetch";
import { graphqlTransport } from "@tahanabavi/typefetch-graphql";
import { grpcTransport } from "@tahanabavi/typefetch-grpc";

const client = new ApiClient(
  {
    baseUrl: "https://api.example.com",
    transports: [
      graphqlTransport({ url: "https://api.example.com/graphql" }),
      grpcTransport({ baseUrl: "https://grpc.example.com" }),
    ],
  },
  contracts,
);
client.init();
```

A route naming a transport with no adapter registered fails at `init()`, with the
endpoint id in the message — not on the first call in production.

## 4. Errors normalize across every wire

This is what makes the whole thing worth doing. `RichError` gains a **`kind`**,
drawn from the gRPC status set because it is the best-designed of the three, and
HTTP status and GraphQL `extensions.code` both map onto it cleanly:

```ts
client.onError((error) => {
  if (error.kind === "unauthenticated") redirectToLogin();
});
```

That one handler now fires for an HTTP 401, a gRPC `UNAUTHENTICATED`, and a
GraphQL `UNAUTHENTICATED` alike.

| `ErrorKind` | | |
| --- | --- | --- |
| `cancelled` | `invalid_argument` | `deadline_exceeded` |
| `not_found` | `already_exists` | `permission_denied` |
| `unauthenticated` | `resource_exhausted` | `failed_precondition` |
| `aborted` | `out_of_range` | `unimplemented` |
| `internal` | `unavailable` | `data_loss` |
| `network` | `validation` | `unknown` |

The **typed** error body stays transport-specific, because that is the part that
must match your server exactly. Unambiguous, since a route has exactly one
transport:

| Transport | `errors` key | `status` | Also carries |
| --- | --- | --- | --- |
| `http` | HTTP status (`404`) | HTTP status | — |
| `grpc` | gRPC code (`5`) | mapped HTTP status | `grpcCode` |
| `graphql` | `extensions.code` (`"UNAUTHENTICATED"`) | `200` or real status | `graphqlErrors` |

`ErrorResponsesMap` widened from `Record<number, …>` to
`Record<number | string, …>` to allow the GraphQL key space. `Record<number, T>`
is still assignable, so existing contracts are unaffected.

## 5. The new packages

### `@tahanabavi/typefetch-graphql`

Standard GraphQL over HTTP, handling both response media types — legacy
`application/json` (errors inside a 200) and `application/graphql-response+json`
(errors with a real status).

Its headline feature is one no other GraphQL client can offer, because no other
one is Zod-first: **the selection set is generated from the `response` schema.**

```ts
getUser: {
  transport: "graphql",
  operation: "query",
  root: "user",
  request: z.object({ id: z.string() }),
  response: User,  // → query GetUser($id: String!) { user(id: $id) { id name email } }
}
```

One source of truth, so a selection set can never drift from the schema that
validates it. Supply `document` explicitly for fragments, aliases, unions and
nested arguments — and the generator refuses, at `init()`, with the schema path
that defeated it, rather than emitting a query the server would reject.

### `@tahanabavi/typefetch-grpc`

Connect unary JSON by default — the only gRPC-family protocol that is honest
HTTP: real status codes, a JSON error body, no trailers, curl-able. Your Zod
schemas stay the source of truth and no protobuf runtime is installed.

Binary grpc-web sits behind a codec seam, so protobuf never enters any published
package: the adapter owns the 5-byte framing and the trailer frame, the codec
owns only message bytes.

### `@tahanabavi/typefetch-encryption` and `@tahanabavi/typewire-cli`

The encryption middleware and the CLI binary, moved out with their dependencies.
The command is renamed `typefetch` → `typewire`, because one CLI reading one
`typewire.config.ts` serves every package in the family. See the migration table
below.

### `driver` — pinning the terminal sender

`fetch` has no upload-progress API, so the client has always switched to
`XMLHttpRequest` for a request that asked for it. `driver` makes that choice
declarable per endpoint rather than implicit:

```ts
uploadAvatar: {
  method: "POST",
  path: "/avatar",
  driver: "xhr",        // always XHR — upload progress without threading a handler
  request, response,
}
```

| `driver` | Behaviour |
| --- | --- |
| `"auto"` *(default)* | `fetch`, switching to XHR only when a call asks for upload progress. Unchanged. |
| `"fetch"` | Always `fetch`. Pins the modern path where a proxy or polyfill makes the XHR swap undesirable. |
| `"xhr"` | Always `XMLHttpRequest` where it exists; falls back to `fetch` with a one-time warning where it does not. |

XHR has no equivalent for `cache`, `mode`, `redirect`, `referrerPolicy`,
`integrity` or `duplex`, so those `RequestInit` fields are dropped rather than
silently misapplied — the documented gap is better than the quiet one.

## 7. Behaviour changes to plan for

A silent behaviour change is worse than a compile error, so each of these is
listed even where it is an improvement.

1. **A bad request input now throws `RichError`, not `ZodError`.** Previously an
   input that failed its own `request` schema escaped raw: no `kind`, never
   passed to `onError`, invisible to instrumentation — while a bad *response* one
   line later did all four. Both ends of the contract now fail identically.
   Zod's field errors are carried into `RichError.errors`, so nothing is lost.
   **If you catch `ZodError` around a call site, update it to `RichError` with
   `kind: "validation"`.**

2. **`onError` now fires for input-validation failures.** A consequence of (1).
   If your handler shows a toast for every error, it will now show one for a
   validation failure it previously never saw.

3. **Instrumentation emits a `start`/`error` pair for input-validation
   failures.** Previously nothing was emitted. Devtools rows that did not exist
   before will now appear.

4. **`MiddlewareContext.endpoint` is now `AnyEndpointDefZ`.** Middleware reading
   `ctx.endpoint.method` or `.path` still compiles while only the `http`
   transport is registered. It stops compiling the moment you install a transport
   package, because those fields do not exist on every variant. Use
   `describeEndpoint(ctx.endpoint)` or `ctx.init.method` instead.

5. **`errors` map keys are `number | string`.** Existing numeric maps are
   unaffected; the widening exists for GraphQL's string codes.

## 8. Migration

| Before | After |
| --- | --- |
| `import { encryptionMiddleware } from "@tahanabavi/typefetch"` | `import { encryptionMiddleware } from "@tahanabavi/typefetch-encryption"` |
| `import { EncryptionOptions } from "@tahanabavi/typefetch"` | `from "@tahanabavi/typefetch-encryption"` |
| `npx typewire test` (bin in core) | `npm i -D @tahanabavi/typewire-cli`, then `npx typewire test` |
| `import { defineTypeFetchTestConfig } from "@tahanabavi/typefetch"` | `from "@tahanabavi/typewire-cli"` |
| `import { runCli } from "@tahanabavi/typefetch"` | `from "@tahanabavi/typewire-cli"` |
| `import { writeReportFiles } from "@tahanabavi/typefetch"` | `from "@tahanabavi/typewire-cli"` |
| `catch (e) { if (e instanceof ZodError) … }` | `catch (e) { if (e instanceof RichError && e.kind === "validation") … }` |
| `ctx.endpoint.method` in middleware | `describeEndpoint(ctx.endpoint).operation` or `ctx.init.method` |
| `ctx.endpoint.path` in middleware | `describeEndpoint(ctx.endpoint).target` or `ctx.url` |

`EncryptionMethod`, `DeepEncryptionMap` and `EncryptionConfig` **stayed in
core** — they are types with no runtime cost, so an endpoint's `encryption` key
is still declarable without installing the encryption package. You just cannot
execute one.

## 9. Backward compatibility

Everything not listed in §7 and §8 is unchanged.

- **Every existing contract compiles as written.** No `transport` key means
  `"http"`.
- **Every existing call site is unchanged.** `api.user.getUser(input, options)`
  has the same signature and the same return type.
- **`EndpointDef` keeps its name and its HTTP-only meaning**
  (`= EndpointFor<"http", …>`), so existing type annotations resolve to the same
  type.
- **`endpointId` is unchanged**, so `query-core`, `devtools-core`, `react` and
  `devtools` required no changes.
- **`Record<number, ZodTypeAny>` is still assignable to `ErrorResponsesMap`.**
- **The HTTP path is byte-for-byte the previous implementation**, extracted into
  the built-in adapter with no behaviour change. The XHR upload-progress swap,
  the `res.ok` ordering, envelope handling and error-body parsing all behave
  exactly as they did in 1.9.

## 10. Deliberately out of scope

- **Streaming** — gRPC server/bidi streaming and GraphQL subscriptions cannot
  return `Promise<T>` and would change `EndpointMethod`. Unary and
  query/mutation only. Use `@tahanabavi/typesocket` for streams.
- **Typed selection-set inference from a hand-written document** (gql.tada
  style). We generate the document from Zod instead — the inverse, and one fewer
  source of truth.
- **Persisted queries / APQ**, `@defer` / `@stream`, protobuf reflection,
  client-side gRPC load balancing, `grpc-web-text`.
