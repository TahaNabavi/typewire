# TypeFetch Response Types & Transfer Progress

This release adds two things to the client: an endpoint can declare **how its
response body is decoded**, and a request can report **upload and download
progress**. Both are additive — an endpoint without `responseType` and a call
without progress handlers behave **byte-for-byte** as before, and TypeFetch gains
no new runtime dependency.

It also corrects the order in which a failed response is handled, which is a
behavior change worth reading before you upgrade — see
[The `res.ok` fix](#the-resok-fix).

---

## 1. Response types

`responseType` is a new optional key on the contract:

```ts
export const contracts = {
  report: {
    downloadPdf: {
      method: "GET",
      path: "/reports/:id/pdf",
      responseType: "blob", // ← new
      request: z.object({ path: z.object({ id: z.string() }) }),
      response: zBlob(),
    },
  },
} as const;

const pdf = await api.report.downloadPdf({ path: { id: "42" } }); // Blob
```

| `responseType`  | Resolves to                             | Schema helper    |
| --------------- | --------------------------------------- | ---------------- |
| `"json"`        | parsed JSON *(default)*                 | any Zod schema   |
| `"text"`        | `string`                                | `z.string()`     |
| `"blob"`        | `Blob`                                  | `zBlob()`        |
| `"arrayBuffer"` | `ArrayBuffer`                           | `zArrayBuffer()` |
| `"formData"`    | `FormData`                              | `zFormData()`    |
| `"file"`        | `{ blob, filename, contentType, size }` | `zFile()`        |
| `"stream"`      | `ReadableStream \| null` *(undrained)*  | `zStream()`      |
| `"response"`    | the whole `Response` *(untouched)*      | `zResponse()`    |

### Why it lives on the contract

The decoded value is what the endpoint's `response` schema validates. A per-call
`responseType` could therefore make the endpoint's *inferred return type* a lie —
the signature says `Blob`, the call says `text`, and nothing catches it. Keeping
it on the contract makes the declared type and the decoded value one decision.

### Why `zBlob()` and not `z.instanceof(Blob)`

`z.instanceof(Blob)` dereferences the global at **module evaluation** time. In a
project where the contract file is imported by both the browser app and the
server, merely *loading* it throws a `ReferenceError` anywhere `Blob` is absent —
older Node, or an SSR pass. Every helper here defers the lookup into the
validator, so the schema is always constructible and only validation depends on
the environment.

### `responseType: "file"`

The one non-obvious entry in the table. A download endpoint almost always needs
the filename, and the only place it exists is `Content-Disposition`:

```ts
const { blob, filename, contentType, size } = await api.report.downloadFile({
  path: { id: "42" },
});
```

`filename` prefers the RFC 5987 `filename*` form over the plain one, percent-
decodes it, and strips any directory component — a filename is attacker-
influenced data in any app where one user downloads what another uploaded, and it
routinely ends up in a `download` attribute or a write path.

> **CORS.** `Content-Disposition` is not a safelisted response header.
> Cross-origin, `filename` is `undefined` unless the server sends
> `Access-Control-Expose-Headers: Content-Disposition` — even though it *did*
> send the header. Always keep a fallback name.

### What non-JSON types skip

`setResponseWrapper` and `useResponseTransform` run for `"json"` and `"text"`
only. Unwrapping an envelope from a `Blob`, or spreading one through a transform
written for records, would corrupt precisely the payloads these types exist for.

## 2. Upload and download progress

Per-request options, because progress is a call-site concern — the same endpoint
deserves a progress bar in a form and not in a background sync:

```ts
await api.media.upload(
  { body: { file } },
  {
    onUploadProgress: ({ percent, loaded, total }) => setProgress(percent ?? 0),
    onDownloadProgress: ({ percent }) => setDownload(percent ?? 0),
  },
);
```

Each tick:

```ts
type TransferProgress = {
  phase: "upload" | "download";
  loaded: number;
  total?: number;            // only when the length is known
  percent?: number;          // 0–100, two decimals, only when known
  lengthComputable: boolean; // false → render an indeterminate bar
};
```

`total`/`percent` are omitted rather than faked. A `total` of `0` or a missing
`Content-Length` would otherwise produce `Infinity` or `NaN` in a progress bar,
which is worse than admitting the length is unknown.

### `fetch` cannot do upload progress

There is no API for it, and there never has been. The streaming-request-body
workaround (`ReadableStream` body + `duplex: "half"`) is Chromium-only and
requires HTTP/2, so it cannot be the answer for a client that has to work
everywhere.

So when — and only when — a request is given `onUploadProgress`, TypeFetch swaps
the **terminal** transport of the middleware chain for `XMLHttpRequest`, which
can report it. The swap is invisible to everything around it: middleware receives
the same context and is handed a real `Response`, and the entire response path
downstream is unchanged.

Requests without the handler take the byte-for-byte unchanged `fetch` path.

**Known limits of the XHR path**, stated rather than papered over:

* **No `XMLHttpRequest` in Node or SSR.** The request still runs over `fetch`;
  the handler is simply never called. TypeFetch warns once — silently never
  firing would make a working upload look like a hung one.
* **`RequestInit` fields with no XHR equivalent are not carried over**: `cache`,
  `mode`, `redirect`, `referrerPolicy`, `integrity`, `duplex`. `credentials:
  "include"` maps to `withCredentials`. Accepting a value the transport cannot
  honor would be worse than the documented gap.
* **Retries restart progress.** Each attempt re-sends the whole body and opens
  with a `loaded: 0` tick, so a bar visibly resets instead of appearing frozen at
  the previous attempt's percentage.

### Download progress

Runs on the normal `fetch` path, counting bytes off `res.body` as whatever
downstream call actually drains it does so — nothing is buffered to measure it.

`total`/`percent` need a readable `Content-Length`; cross-origin that means the
server must also list it in `Access-Control-Expose-Headers`. Without it you still
get `loaded` ticks with `lengthComputable: false`.

Ignored for `responseType: "stream"` and `"response"`, which hand you the
undrained body — counting bytes there would consume the stream you asked to own.

## 3. In React

`@tahanabavi/typefetch-react` reads progress off the mutation's own state, so a
component needs no `useState` and no extra hook:

```tsx
const upload = useMutation(api.media.upload, { trackProgress: "upload" });

<progress value={upload.progress?.upload?.percent ?? 0} max={100} />;
```

`trackProgress` takes `true` (both directions), `"upload"`, or `"download"`. It
is **off by default** because neither side is free: upload tracking moves the
request to XHR, download tracking re-streams the response body.

Progress lands in `MutationState.progress`, which means it updates through the
same `useSyncExternalStore` subscription as `data` and `error`. It clears when a
new `mutate` starts and on `reset`, and a superseded call's ticks are discarded —
the same rule `data` and `error` already follow.

If you would rather drive an imperative UI, pass `onUploadProgress` /
`onDownloadProgress` in the mutation options instead.

## 4. Devtools

`RequestEvent` gains a `progress` variant, and `InspectorBridge` gains a matching
**separate channel**: `recordProgress()` / `getProgressSnapshot()`.

Progress deliberately does not go through `record()`. A single large upload emits
ticks continuously; routing them into the ring buffer would copy a 500-element
array per tick and evict the page's entire real event history inside one request
— the exact opposite of what an inspector is for. Instead each in-flight call
keeps exactly one latest-only entry, released when the call concludes.

`selectEntries(events, progress?)` takes the snapshot as an optional second
argument and joins it onto the matching row as `entry.progress`.

Progress events are emitted **only** for requests that asked for progress.
Attaching instrumentation never enables it — opening devtools must not change
which transport a request uses.

## 5. The `res.ok` fix

Previously the response body was decoded with `res.json()` **before** `res.ok`
was checked. Any failure whose body was not JSON therefore threw a raw
`SyntaxError`, and the HTTP status — the single most useful fact about the
failure — never reached the caller. That covers a lot of real failures: an HTML
error page from a proxy, an empty body from a gateway, a plain-text 503.

Failed responses are now handled first, and their body is read as text and *then*
parsed:

| Failure body        | Result                                              |
| ------------------- | --------------------------------------------------- |
| JSON                | parsed; `data` typed against the `errors` map        |
| HTML / plain text   | raw text in `error.detail`                          |
| empty               | still a `RichError` carrying `status`               |
| JSON scalar         | stringified into `error.detail`                     |

`message` falls back through the body's `message`, then `statusText`, then
`HTTP <status>`.

**This is a behavior change.** If you have a `catch` that special-cases the old
`SyntaxError`, it now receives a `RichError` instead.

One behavior was deliberately **preserved**: an API envelope that answers
`{ success: false, message }` alongside a 4xx still surfaces the envelope's
message. The envelope is now consulted with `safeParse`, so a failure body that
doesn't fit it falls through to the status-based error instead of throwing a
validation error over it — which is what the old `parse` call did.

## 6. `onError` fires once

`onError` used to fire once per *layer* that saw an error on its way out, not
once per failed request:

| Configuration       | Calls before | Calls now |
| ------------------- | ------------ | --------- |
| plain HTTP failure  | 2            | 1         |
| `maxRetries: 2`     | 4            | 1         |

Every failure path now routes through one internal `report()` that is idempotent
per error instance, and the reporting point sits outside the retry loop. A
global error handler exists to fire a toast or redirect on a 401 — doing that
three times for one failed request, or once per retry attempt, was never the
intent.

Unchanged: which errors reach `onError`, the error instance handed to it (the
same object the caller catches), and the fact that a request whose retry
eventually succeeds reports nothing at all.

**This is a behavior change.** If you were de-duplicating calls in your handler,
remove that.

---

## Compatibility

* No new runtime dependency.
* An endpoint without `responseType` decodes as JSON, as always.
* A request without progress handlers uses `fetch`, unchanged.
* A `Response` stand-in that only implements `json()` — common in test doubles
  and hand-rolled middleware — is still read correctly; the text-first path is
  used only when `text()` is actually available.
* The one behavior change is the error path described above.
