# v0.1.0 — the TypeWire CLI

`@tahanabavi/typewire-cli` is the command-line half of TypeWire: the `typewire`
binary, one `typewire.config.ts` for every package in the family, and a
project-detecting `init` that wires a codebase up in one command.

It exists as a separate install for the same reason adapters do — **anything
that needs a dependency ships separately.** The CLI used to live inside
`@tahanabavi/typefetch`, which meant every consumer of a typed HTTP client
installed `jiti`, a TypeScript loader no browser bundle will ever need. The
precedent is well understood: `prisma` / `@prisma/client`, `drizzle-kit` /
`drizzle-orm`.

---

## 1. `typewire init` — read the project, then ask

```bash
npx typewire init
```

It detects framework, language, package manager, `src/`, monorepo layout and
which `@tahanabavi/*` packages are already installed, then asks one question:

```txt
  project    acme-shop
  framework  Next.js
  language   TypeScript
  installer  pnpm
  source     src/

What does this project need?
    • [•] typefetch — typed HTTP client
   1  [✓] Query layer — caching, dedup, declared invalidation
   2  [ ] typesocket — typed WebSocket contracts
   3  [✓] Devtools panel — request timeline and cache inspector
   4  [ ] GraphQL transport
   5  [ ] gRPC transport
```

Everything detected is a **default, shown and overridable** — never a silent
decision, because a wrong guess that nobody sees is worse than no guess at all.
Options that cannot apply are not offered: no devtools panel in an Express
project, no NestJS adapter outside NestJS.

It then scaffolds a `typewire/` folder wired for the selection, prints the
install command for *your* package manager, and lists what to do next.

**The framework changes what is generated, not only where it goes:**

| Project | What differs |
| --- | --- |
| Next.js | `"use client"` on the provider and devtools panel — without it the App Router fails at build |
| Vite | `import.meta.env.VITE_API_URL`, read through a guard so the CLI can load the same file under Node |
| Node / Express | `process.env.API_BASE_URL` |
| No TypeScript | `.js` / `.mjs` files, no `as const` |

| Flag | Meaning |
| --- | --- |
| `--yes` | Take every detected default, ask nothing |
| `--features <a,b>` | Skip the question — reproducible in CI |
| `--contracts-path <path>` | Use contracts you already have |
| `--output <dir>` | Scaffold elsewhere |
| `--dry-run` | Print the plan, write nothing |
| `--force` | Replace existing files instead of skipping them |

Without a TTY it takes the defaults and **prints what it chose** rather than
blocking on a prompt nobody can answer. An unknown `--features` value is an
error, not a silent no-op — the point of the flag is a reproducible scaffold,
and quietly dropping a typo produces a project missing exactly what was asked
for.

### One definition of the client

The generated `client.ts` exports a factory and the adapter list; the generated
config **imports both**:

```ts
// typewire/client.ts
export const transports = [graphqlTransport(), grpcTransport()];
export function createClient(options: { baseUrl?: string; token?: string } = {}) { … }

// typewire.config.ts
import { createClient, transports } from "./src/typewire/client";
```

A second client built inside the config drifts the moment a middleware, a
transport or an auth header is added to one of them — and then `typewire test`
exercises a client the app does not ship.

## 2. `typewire.config.ts`

One file, one section per package, so nothing needs renaming when a package is
added and a project using only typefetch writes only that section.

```ts
export default defineConfig({
  lint: { rules: { "path-params-declared": "error" } },

  typefetch: {
    contracts,
    createClient,
    transports,
    test: { options: { mode: "full" }, report: { output: "./typewire-report/report" } },
  },
});
```

**`contracts` is the only always-required key.** A client is required by the
commands that actually make requests and by nothing else, so `list` — and later
`lint`, `diff`, `explain` — run against a contract file with no API reachable.
That is the difference between a check that runs on every commit and one that
never gets wired up.

| Feature | Why |
| --- | --- |
| Discovery walks up from cwd | a package in a monorepo inherits the root config |
| `extends` (path or package) | shared base, per-package overrides |
| Config as a function | `({ mode, command, ci }) => …` — one file, several environments |
| tsconfig `paths` in the loader | a contract importing `@/schemas` actually loads |
| `transports` | contracts-only commands can describe a gRPC route without a client |
| Validation names the key | `typewire.config.ts › typefetch.contracts — expected an object of contract modules, received undefined` |

### `projects` — several API surfaces

A repo with a dashboard API, an admin API and a landing API declares them in one
file, each with its own contracts, client, middleware and base URL:

```ts
export default defineConfig({
  lint: { rules: { "path-params-declared": "error" } },   // shared default
  projects: {
    dashboard: { typefetch: { contracts, createClient: createDashboardClient } },
    admin: {
      typefetch: { contracts: adminContracts, createClient: createAdminClient },
      diff: { baseline: "admin.lock.json" },
    },
    landing: { typefetch: { contracts: landingContracts } },
  },
});
```

Three rules make it safe rather than merely possible:

1. **Every project runs by default**, and any failure fails the command. A gate
   that checked one of three surfaces and reported green is worse than no gate.
   `--project <a,b>` narrows it.
2. **Reports are written per project.** One shared output path means the last
   project overwrites the rest, and the report looks complete while describing a
   single API.
3. **Commands needing exactly one project refuse to guess** — the error names
   what is available.

Single-API configs omit the key and resolve to one *implicit* project, so no
command branches on which shape was written.

## 3. Commands

| Command | What it does |
| --- | --- |
| `typewire init` | Detect, ask, scaffold |
| `typewire test` | Contract test runner + reports (default command) |
| `typewire list` | Every route, through its own transport's `describe()` |
| `typewire release-doc <version>` | Scaffold `docs/releases/vX.Y.Z.md` |

`list` never reads `method`/`path` off an endpoint — those exist only on http
routes. It asks the adapter, so a gRPC row prints
`unary user.v1.UserService/GetUser`, and when a transport cannot be described it
says so and names it rather than printing a `?` that reads as complete.

## 4. Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Success |
| `1` | Findings — tests failed |
| `2` | Misconfiguration — config missing, invalid, or the command called wrong |

A CI job gating on findings needs to tell "your contracts have problems" apart
from "your pipeline is broken". Output also respects `NO_COLOR`, `CI` and
non-TTY stdout: ANSI escapes in a piped report break `grep`.

## 5. Migration

```diff
- import { defineTypeFetchTestConfig } from "@tahanabavi/typefetch";
+ import { defineConfig } from "@tahanabavi/typewire-cli";
```

```bash
npm i -D @tahanabavi/typewire-cli
```

| Before | After |
| --- | --- |
| `npx typefetch` | `npx typewire` |
| `typefetch.test.config.ts` | `typewire.config.ts` |
| `defineTypeFetchTestConfig({ contracts, … })` | `defineConfig({ typefetch: { contracts, … } })` |
| `options` / `context` / `report` at the section root | under `test` |
| `--package <name>` on `init` | removed — the wizard knows the package names |
| default report path `./typefetch-report/report` | `./typewire-report/report` |

**Your existing config still loads.** A `typefetch.test.config.*` file is found,
its flat shape lifted into the `typefetch` section, and a warning printed once
naming the new file. The loose `options`/`context`/`report` keys are still
accepted with a warning. Both are scheduled for removal in v3, and both are
handled by the planned `@tahanabavi/typewire-codemod`.

## 6. Behaviour changes to plan for

| Change | Why |
| --- | --- |
| `release-doc` now works | it was in `--help` since 1.6.0 with no case in the command switch, and silently ran the test suite instead |
| Bad usage exits `2`, not `1` | `1` is reserved for findings, which is the code a CI gate is allowed to expect |
| Colour is suppressed off-TTY and under `CI`/`NO_COLOR` | escapes in a piped report break `grep` |
| `list` gained `Transport` and `Operation` columns | a listing that shows only method/path is wrong once a second transport exists |

## 7. Dependencies

`jiti`, and nothing else — pinned in `scripts/assert-no-deps.mjs`. It is a
devDependency of your project, so none of it reaches a production bundle.

## 8. Deliberately out of scope

`snapshot`, `diff`, `lint`, `doctor`, `explain`, `mock` and `generate openapi`
are designed in [`docs/CLI.md`](../../../../docs/CLI.md) and not built. `diff` —
breaking-change detection against a committed API-surface lockfile, including
the case no server-side differ catches, *a new enum variant in a response is
breaking for a validating client* — is the one that earns the split, and it
comes next.
