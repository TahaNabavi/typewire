# v0.1.0 — the panel catches up with the wires

`@tahanabavi/type-devtools` is the React inspector: one timeline, a live query
cache, a runtime override editor, and a settings tab — dropped into an app as a
single component, with no stylesheet.

This release is what the panel had to become once one typefetch client started
speaking REST, GraphQL and gRPC. It also renders something the core had been
recording for a release already and the panel was throwing away.

See [`type-devtools-core` v0.1.0](../../../devtools-core/docs/releases/v0.1.0.md)
for the store-level changes this builds on.

---

## 1. The badge shows the wire

Every row used to be badged `http` or `ws` — the *client* that produced it. With
one client speaking three protocols, that meant a GraphQL query, a gRPC unary
call and a REST GET were three identical-looking rows.

The badge now reads `http` / `graphql` / `grpc` / `ws`, colored per wire, taken
from `entry.transport` and falling back to `entry.source`. The fallback is never
a guess: typesocket has exactly one wire, and a typefetch older than the
transport registry only ever had one either.

A third-party adapter gets a badge with its own `kind` and a neutral color,
rather than no badge. The transport registry is open, so that is a supported
case rather than an unhandled one.

## 2. The wire filter is built from the traffic

The filter was three hard-coded chips: `all` / `http` / `ws`. There was no way
to isolate GraphQL rows, because the panel did not know GraphQL existed.

The chips are now derived from what actually arrived, ordered `http`, `graphql`,
`grpc`, `ws`, then anything else alphabetically — a fixed order rather than
first-seen, so the row of chips does not reorder itself under the cursor as
traffic lands.

Two rules make it behave:

- **Hidden when everything went over one wire.** A filter with one option
  filters nothing, and a REST-only app has no use for a `graphql` chip it can
  never select.
- **Always visible while a filter is active.** Otherwise clearing the timeline
  while filtered would remove the only chip that could turn the filter back off,
  and the panel would look permanently empty with no way out.

## 3. Failures say what went wrong

A failed row shows its `ErrorKind` beside the status, and the detail pane shows
it alongside the HTTP status when there is one:

```txt
grpc   user.syncUser        not_found  error   41ms
```

This is the field to scan on a mixed timeline. gRPC and GraphQL carry no HTTP
status, so before this the row could only say `error` — technically true, and no
help at all. `404`, gRPC code `5` and GraphQL `extensions.code: "NOT_FOUND"` all
read as `not_found`.

## 4. Live transfers, finally rendered

`devtools-core` has recorded upload and download progress since the transfer
release. The panel called `selectEntries(events)` — without the progress
snapshot — so a 200 MB upload showed a static `pending` row for as long as it
took.

Now:

- a bar under the row, filling as the transfer advances;
- `↑ 62% · 1.2 MB / 2.0 MB` in the detail pane;
- an **indeterminate** moving bar when the server reports no total, which is the
  common case for a chunked response. A bar stuck at zero would read as a stall.

The bar clamps at 100%: a server may report `loaded > total`, and the fill must
not overflow its track. It disappears the moment the call concludes, because the
bridge releases a concluded call's progress.

The progress store is bound separately through `useInspectorProgress`, so a
custom panel that draws no bars never subscribes to it — the same separation the
core keeps between the two stores.

## 5. Search covers the new fields

`not_found` and `grpc` now narrow the list the way an endpoint name does. Those
are the two things you actually type when hunting a bug across a mixed timeline.

## 6. cURL is offered for REST only

The button reconstructs a command from the start event's method and URL. On
GraphQL those are `query` and a root field, so it was producing:

```bash
curl -X query 'https://api.example.com/user'
```

which is not a command anyone can run. Rebuilding the real POST means rebuilding
the document and the envelope — that belongs to the adapter, not the panel — so
the button is simply absent on non-REST rows rather than present and wrong.

## API additions

| Export | |
| --- | --- |
| `useInspectorProgress(bridge)` | the progress store, bound to React |
| `useInspectorEntries(bridge)` | now joins progress onto the rows automatically |
| `transportOf(entry)` | the wire a row used, falling back to its source |
| `transportColor(palette, wire)` | the badge color for a wire |
| `statusColor(palette, status)` | the color for a row's status |
| `InspectorProgress` | re-exported from the core |

`Palette` gained `graphql` and `grpc`. A custom palette object must supply them;
the two built-in palettes already do.

## Backward compatibility

- `<TypeDevtools bridge={…} />` is unchanged — every prop, every test id.
- The `typewire-filter-*` test ids are unchanged for the wires that are present.
- Nothing was renamed or removed from the public surface.
- A bridge fed by a client that reports no transport renders exactly as before,
  because the badge falls back to `source`.
